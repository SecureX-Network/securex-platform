# SecureX Backend Deployment on Render (Free Plan)

Deploys the complete SecureX backend ecosystem as code from **ONE Render
Blueprint** connected to **`SecureX-Network/securex-platform`** (the source of
truth is the `render.yaml` in that repo):

```
securex-platform/render.yaml  (master Blueprint)
├── securex-api             (Web Service, Node   - repo: securex-platform)
├── securex-postgres        (Render PostgreSQL   - managed by the Blueprint)
├── securex-blockchain      (Web Service, Node   - repo: securex-blockchain)
└── securex-fraud-engine    (Web Service, Python - repo: securex-fraud-engine)
```

| Service | Repo | Type | Public URL | Health path |
|---|---|---|---|---|
| `securex-api` (Platform API) | `SecureX-Network/securex-platform` | Web (Node) | `https://api-securex.sp-net.in` (+ `*.onrender.com`) | `/api/health` |
| `securex-postgres` (PostgreSQL) | same repo | Managed Postgres | private + public | — |
| `securex-blockchain` (CTN node) | `SecureX-Network/securex-blockchain` | Web (Node, PoA) | `https://<blockchain>.onrender.com` | `/ready` |
| `securex-fraud-engine` (FastAPI) | `SecureX-Network/securex-fraud-engine` | Web (Python) | `https://<fraud-engine>.onrender.com` | `/ready` |

All services, database included, run on Render's **free** plan: **$0/month**.

The Vite frontend/SPA is **not** built by Render. It is deployed by Vercel at
`app-securex.sp-net.in` (same monorepo, separate deployment). Render serves
only JSON APIs.

## Free-plan implications (read before deploying)

- **The blockchain ledger is ephemeral.** Free web services cannot attach a
  persistent disk and may be restarted/replaced at any time. When an instance
  is replaced, `.ctn/` is wiped: on next boot `scripts/provision.mjs`
  regenerates a fresh node identity and the chain re-initialises from genesis.
  Treat the chain as a demo/reset-on-redeploy ledger on this plan.
- **Free Postgres expires 30 days after creation** (1 GB, no backups). After
  expiry you have 14 days to upgrade before deletion. The API is self-healing:
  `SEED_ON_BOOT=true` recreates schema + canonical seed data on a fresh
  database (idempotent — never overwrites existing rows).
- **No private networking into free web services.** Free instances can send
  private requests (e.g. to the database) but cannot receive them, so the
  blockchain and fraud engine are public web services and the Platform API
  reaches them over their `*.onrender.com` URLs.
- **Cold start/sleep.** Free web services sleep after ~15 min of inactivity and
  restart on the next request (a few seconds).
- **`$PORT` (10000).** Render proxies inbound traffic to `$PORT`. The Platform
  API already reads `PORT`; the provision script binds the blockchain API to
  `$PORT`; fraud's start command binds `${PORT:-8000}`.

## 1. Prerequisites

- `render` CLI v2.7+ (auth: `render whoami`) and a Render account with a
  workspace.
- `gh` auth with write access to the three `SecureX-Network` repos.
- DNS access to `sp-net.in` (for the custom API domain).

## 2. Commit the master Blueprint

The single source of truth is [`render.yaml`](../render.yaml) in
`securex-platform`. It defines all **four** resources, and the `repo:` field on
each service tells Render which repository to clone source from:

- `securex-api` → `SecureX-Network/securex-platform`
- `securex-blockchain` → `SecureX-Network/securex-blockchain`
- `securex-fraud-engine` → `SecureX-Network/securex-fraud-engine`
- `securex-postgres` → managed by the Blueprint (no repo)

`render.yaml` was intentionally **removed** from `securex-blockchain` and
`securex-fraud-engine` so that a second Blueprint can never claim those
resources (Render: each resource must be managed by at most one Blueprint).

Validate offline:

```bash
render blueprints validate render.yaml   # in ctn-platform
```

Expect: `valid: true` with exactly **4 resources** (3 services + 1 database).

## 3. Create the Blueprint (dashboard — the one manual step)

The render CLI cannot apply/sync Blueprints, so this runs in the dashboard:

1. Render Dashboard → **New +** → **Blueprint**.
2. Connect **one** repository: `SecureX-Network/securex-platform` (branch
   `main`). Do **not** connect `securex-blockchain` or `securex-fraud-engine`
   to any Blueprint.
3. Review the plan: exactly 4 resources — Web Service `securex-api`,
   PostgreSQL `securex-postgres`, Web Service `securex-blockchain`, Web
   Service `securex-fraud-engine`.
4. **Create resources.** `JWT_SECRET`, `SECRET_KEY` and `API_KEYS` are
   auto-generated by the Blueprint (`generateValue`).
   The managed database `securex-postgres` is provisioned by the Blueprint — do
   not create it separately.

## 4. Wire the downstream URLs (post-sync)

1. Open the created `securex-blockchain` service → copy its URL, e.g.
   `https://securex-blockchain-s2k3.onrender.com`.
2. Open `securex-fraud-engine` → copy its URL.
3. Open `securex-api` → **Environment** →
   add two env vars and **Save Changes** (triggers a brief redeploy):
   ```
   BLOCKCHAIN_API_URL   = https://securex-blockchain-XXXX.onrender.com
   FRAUD_ENGINE_URL     = https://securex-fraud-engine-XXXX.onrender.com/fraud
   ```
   The Platform API only probes these for the Security Center health report
   (`/health` on the origin); until set, `/api/health` shows them DEGRADED.

## 5. Custom domains + DNS

- `api-securex.sp-net.in` → CNAME to the `securex-api` onrender URL
  (`api-securex-sp-net-in.onrender.com`). Render provisions the TLS cert after
  the record resolves.
- `app-securex.sp-net.in` → handled on Vercel (frontend; not part of this
  blueprint). Make sure its backend URL vars are set there (step 6).

## 6. Frontend (Vercel) env vars

Set these on the app-role deployment of the monorepo frontend:

```
VITE_API_BASE_URL          = https://api-securex.sp-net.in/api
VITE_BLOCKCHAIN_API_URL    = https://securex-blockchain-XXXX.onrender.com
VITE_USE_MOCK              = false
```

`VITE_FRAUD_ENGINE_URL` has no frontend consumers — the fraud engine is only
probed by the Platform API backend. Never put secrets in `VITE_*` vars (they
ship to the browser).

## 7. Verify

```bash
curl https://api-securex.sp-net.in/api/health            # ok, database connected, downstreams UP
curl https://<blockchain>.onrender.com/ready              # {ready:true,...}
curl https://<blockchain>.onrender.com/health             # height/status/heartbeat
curl https://<fraud-engine>.onrender.com/ready            # {status:"ready"}
curl https://<fraud-engine>.onrender.com/health           # HealthResponse
```

Then in the app: log in → issue a credential (SX- ID) → verify → open the
ledger explorer (blocks/height feed from the blockchain service) → verify a
revoked credential shows `REVOKED`.

## 8. Operations notes

- **Recovery after a blockchain instance replacement:** nothing to do — the
  node boots to genesis automatically. Re-issued credentials get new on-chain
  entries; historical stored `transaction_hash` rows on the API DB will no
  longer match a reset chain. Use the audit/verification views for the current
  chain state.
- **Postgres 30-day expiry:** before expiry, either upgrade to a paid plan
  (blueprint `plan:` → e.g. `0.5c-1g`) or export data, then create a fresh free
  database; `SEED_ON_BOOT=true` restores schema + seeds.
- **Changing plans later:** flip `plan:` (e.g. `0.5c-512mb`) and re-sync the
  blueprint. A paid web service then supports a **persistent disk** — add a
  `disk:` block to `securex-blockchain`, set `CTN_IDENTITY_DIR`/`CTN_DATA_DIR`
  to the mount path (e.g. `/data/.ctn`, `/data/ledger`) so identity + ledger
  survive restarts. Keep `npm run build` in the build command and let
  `scripts/provision.mjs` regenerate identity if the disk is ever wiped.
- **Adding a validator network:** list node IDs in `CTN_VALIDATORS` (comma-joined)
  and set `CTN_BOOTSTRAP_NODES` to `ws://` URLs of the peer services.
- **Secrets:** never hardcode `JWT_SECRET`/`SECRET_KEY`/`API_KEYS`; the
  blueprint uses `generateValue`. `DATABASE_URL` comes from `fromDatabase`.
